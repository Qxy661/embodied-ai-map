# ⑤ 部署

> 模型在论文里跑得通，和在车上/机器人上跑得动，是两件事。

## 这一环要回答什么

两个约束，一个都不能违反：

1. **算力**：模型的体积、显存、算力需求，装不装得进目标平台？
2. **延迟**：单次推理的时间，撑不撑得住闭环的控制频率？

第二个约束是这一环所有工程方案的来源。

## 分层：整个领域唯一收敛的架构答案

**这是本图三条跨域收敛之一，也是分量最重的一条。**

问题：一个够大的 VLA / VLM 单次推理要几十到几百毫秒，而底层控制要 100–1000 Hz。**单层 VLA 撑不住实时控制**——差距不是优化能补上的。

解法：分层。多个独立团队收敛到了结构同构的方案：

| 系统 | 结构 | 分工 |
|---|---|---|
| Figure Helix | S2 (7B) / S1 (80M) / S0 (10M) | 语义 / 视觉运动 / 关节控制 `!CITE` |
| NVIDIA GR00T N1 | System 2 / System 1 | 慢思考 / 快执行 `!CITE` |
| Gemini Robotics 1.5 | 云端慢脑 + 本体快脑 | 高层推理 / 实时执行 `!CITE` |

**行业共识是"不要正面解决延迟"**：不是把大模型加速到 1 kHz（做不到），而是**让慢脑算得慢但算得对，让快脑高频地把慢脑的意图补成连续动作**。

这解释了一个反常现象：**具身推理的延迟要求至今没有统一定义，因为架构上绕开了它。** 与其问"VLA 要做到多少赫兹"，不如问"慢脑多久说一次话才不耽误快脑"。

**代价**：慢脑的表达能力被快脑的接口带宽限制住了。慢脑每 100 ms 只能说一次话，快脑要在这 100 ms 里自己编出几百个控制周期。所以快脑不是"小一点的慢脑"，它承担的是完全不同的任务——把稀疏的意图变成密集的轨迹。

## 算力与编译

- **平台**：车载侧有 NVIDIA Orin / Thor、地平线征程系列等；机器人侧以 Jetson 系列和各家自研 SoC 为主。选型决定的不是峰值算力，而是**支持哪些精度、有没有对应算子**。
- **编译栈**：ONNX 作为交换格式，TensorRT / 各家编译器做图优化、算子融合、kernel 自动调优。**同一个模型，编译前后差几倍延迟是常见的**——这一层的收益往往比换模型更大。
- **量化**：最直接的压缩手段，但它的收益**不是自动的**（→ ⑤-01）。

## 一条容易被忽略的联动

⑤ 环的选择会反过来改 ③ 环的结论。比如动作分块的可行长度取决于单次推理延迟——如果 TensorRT 把延迟从 60 ms 压到 15 ms，可行的 chunk 长度和整个延迟预算都会重算。**这也是为什么要分环讨论而不是分章节：环之间是耦合的。**
