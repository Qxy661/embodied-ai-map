# 1 kHz 环的抖动预算

> 环 ④ 执行 · 层级 **主** · 证据 `self`（实测，`volatile`）

## 直观

上面所有块都建立在同一个假设上：**底下的关节伺服环按时到达。** 这条环跑 1 kHz，周期 1000 µs。动作分块、实时分块、整条延迟预算，全都默认这个环不掉拍。

这一块就是去测这个假设在这台机器上成不成立。

把线程叫醒只有两种办法：

- **睡**——到点就 `sleep`，把核心让出去。客气，但粗。
- **自旋**——拿 `while` 死转，烧着一个核等。准，但自私。

直觉上自旋应该完胜：它不用等内核调度器醒过来。实际测下来，这个直觉**只在一种条件下成立，而那种条件恰恰是机器人部署里最难满足的那条。**

## 机制

设定：周期 1000 µs，抖动预算取传统口径——周期的 10%，即 **100 µs**。每轮每条件测 1200 个周期，跑 3 轮，**合计 3600 个样本**；竞争条件是另开 8 个死循环线程抢核。

先看**中位数**，也就是大多数人会拿去汇报的那个数：

| 条件 | p50 |
|---|---|
| 睡·空闲 | 307.78 µs |
| 自旋·空闲 | 0.2 µs |

**自旋的中位数好 1000 倍以上。** 只看这一行，结论已经写完了，而且写错了。

问题在于 1 kHz 环的合格线不在中位数上。控制器每个周期都要准时，一次迟到就是一个周期的误差。要看的不是一半的周期怎么样，而是**有多少个周期超了预算**：

> **睡·空闲：83.14% 的周期超预算。**

也就是说，在通用 OS 上"睡到点"根本不是一条 1 kHz 的环——**它每五个周期里就有四个是迟到的。** 自旋把这个数压低**至少 2 倍**。

这里只敢给下界，是因为**自旋那一侧本身就不可引用**：它空闲时每轮的低头比例能从个位数百分比摆到二十几个百分比，于是这个比值跨轮次翻十几倍是常事。所以 `run.py` 只报一个断言的常数下界，而不是本轮测出来的那个漂亮数字——**报本轮值就是在报一次抽签结果。**

同一个实验，换个统计量，结论从"自旋好 1000 倍以上"变成"自旋好 2 倍以上"。两个数都对，但只有后一个对应产品能不能做出来。

**再看 p99，这个统计量根本不能用来排序。** 1200 个周期里的 p99 是**从最差往回数第 12 个**样本——单个样本决定判决。三轮之间，睡法与自旋 p99 的比值摆幅**至少 3 倍**，且方向都不保证：单跑一轮，完全可能测出"睡比自旋的尾更稳"。这也是本块标为 `volatile` 的原因——**它的头号教训就是不要相信单次测量。**

## 边界

这块的边界比大多数块大，因为它测的是活机器：

- **最强的反直觉结论：自旋的优势完全依赖"独占这个核"。** 加上 8 个竞争者之后，自旋的中位数从 0.2 µs 塌到与睡法同量级，**实测每一轮都不如睡法**。自旋是拿"不让出 CPU"换精度，一旦有人抢，它两头都输——而机器人本体上最不缺的就是抢 CPU 的进程。
- **有竞争时，两种办法都基本报废**：睡法 99.78% 的周期超预算，自旋 87.67%。这不是"哪个更好"的问题，是**通用 OS 上任何时序承诺都会被同机负载直接推翻**。
- **绝对数字不可迁移，比值也不可迁移。** 这是 Windows，不是 PREEMPT_RT。在打了实时补丁、核已隔离、进程 `SCHED_FIFO` + `mlockall` 的 Linux 上，隔离核上的自旋通常**真的**赢，排序会翻过来。所以本块声明为 `volatile`，`check_numbers.py` 对它做近似核对而非逐位核对——机器不是同一台机器两次。
- **可迁移的是方法，不是数字**，三条：①别信中位数，要数超预算的周期数；②别信 p99，它是单序统计量，要报分布或超限比例；③必须带负载测，空闲时的数字没有采购价值。
- **本块没测的东西**：内核抢占延迟本身、中断延迟、缓存与内存带宽干扰、EtherCAT 那种亚微秒级同步。工业界在这层的规范做法是一整套（PREEMPT_RT + 核隔离 + `SCHED_FIFO` + `mlockall`，配 EtherCAT 分布式时钟），本块只测了最表层的一段——**在毫无实时保障的通用 OS 上会糟到什么程度**，用来说明那套规范是必需品而不是优化项。

## 脉络

④-01 说通用 OS 给不了时序保证 → ④-02 说那就得靠实时内核和隔离核把这层补上 → 而这一切之上，⑤ 说模型本身的延迟还要再砍一刀。三块连起来是同一件事：**执行侧的确定性是买来的，不是免费的**，而它决定了下游所有分块策略还剩多少余量。
